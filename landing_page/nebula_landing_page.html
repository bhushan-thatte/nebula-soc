The problem

Timing closure is slow, manual, and easy to get subtly wrong

A synthesized RTL design is only useful if every signal reaches its destination before the next clock edge. When it doesn't, engineers read timing reports by hand, trace the dominant delay cells, and figure out the right structural fix — pipelining, retiming, or restructuring logic — without breaking function.

Nebula SoC is a deliberately real testbed for automating that loop: 5 clock domains, 4 independent clocks, 6 generated clocks, and 4 asynchronous CDC bridges, synthesized end-to-end against the open SKY130HD standard cell library — not a toy example.

Data flows A → B → C → D → E, crossing every clock domain in the design via async FIFOs, with domain E's trigger wired back into domain A's command input.
A real debugging detour

Early on, the timing report showed a -429.95ns TNS spike that looked catastrophic. It wasn't a datapath bug — it was an unconstrained reset-recovery check on a synchronizer output, scaling with register count.

Fixed with one targeted false-path exception once the real net was traced through the post-synthesis netlist:

set_false_path -through [get_pins u_domain_c.u_rst_dsp.sync_rst_n*/Q]
What a setup check actually measures

A setup check passes only when data arrival time lands before T1 minus the flip-flop's setup requirement. Nebula's 16 real violations were exactly this — one specific combinational path, per endpoint, arriving too late.

The GenAI engine

A local model, reading real timing reports

Every genuine setup violation was parsed from OpenSTA's report_checks output, then handed to qwen2.5-coder:7b running locally through Ollama — GPU-accelerated, no API key, no cost. The prompt constrained the model to six real, standard timing-closure techniques, after an earlier unconstrained attempt hallucinated a fictional adder architecture.

ADD_PIPELINE_STAGE11 / 16
RETIMING5 / 16
Actual model reasoning — worst violation, pre-fix

The model correctly identified the dominant delay-contributing cells directly from the report's timing arcs, rather than guessing generically:

sky130_fd_sc_hd__ha_1 sky130_fd_sc_hd__fa_1

Recommendation: split the adder tree with an additional pipeline register between Level 1 and Level 2, matching the ripple-carry delay chain the report showed. This became reg_s1_0 through reg_s1_7 — the fix that closed the design.

Formal verification

Proven equivalent, not just re-tested

The GenAI fix changes pipeline latency (2-cycle → 3-cycle), so standard zero-latency EQY checking doesn't directly apply. A latency-matched wrapper reduces it to a standard cycle-accurate equivalence problem, checked with EQY / SymbiYosys.

Proven equivalent

result_valid — control & latency path

Full k-induction succeeds unconditionally at depth 6 and depth 8 using the sat strategy. The valid-signal timing alignment between pre- and post-fix designs is proven correct for every reachable state.

Bounded proof

result_out — 24-bit datapath

Base-case BMC passes cleanly for all 8 cycles from reset — covering the full pipeline-fill transient plus steady state. Full unbounded induction hits known SAT/SMT scaling limits on the 24×16-bit multiply; the induction counterexample traces to an unreachable, X-propagated initial state, not a real functional bug.

Scaling exploration

What we tried beyond the submitted design

FIR tap scaling (16 → 128 taps) works cleanly. A 128-tap Domain C reaches 61,633 cells standalone, 23,266 cells full-design, with a single well-understood -1.16ns/-50.44ns clk_dsp violation — the same category already solved above, just not re-closed for this submission.

Domain B memory-depth scaling (64 → 2,048 entries) hit a genuine architectural wall. With no SRAM compiler in the open-source flow, memory synthesizes as flip-flop arrays where write-data fans out combinationally to every entry. At 2,048 entries, one net reached 2,049 fanout loads, adding 23+ ns of buffer delay — independent of pipelining.

The fully-verified, zero-violation Milestone 4 design was kept as the submitted result. These findings are documented in the repo as supplementary engineering depth, not claimed as part of the closed design.
